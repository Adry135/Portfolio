Marketing & Campaigns

Marketing couldn't say which campaign actually drove pipeline.

Problem: web traffic lived in the web analytics tool, leads lived in the CRM, and nothing linked a click to a deal. Campaign reports counted sessions, not customers.

campaign-performance.dashboard
Open rate % by campaign
Sessions by channel, last 6 months
Conversion funnel: click → lead → opportunity → won
ROI % by campaign
Challenge
Defined a UTM convention and a Deluge script that captures URL parameters into Lead fields at form submission, so every lead carries its source campaign into Zoho CRM.
What the data revealed
Once campaigns were joined to their touchpoints, campaigns with many touchpoints looked far more successful than they were: the one-to-many join was counting the same lead several times. Pre-aggregating touchpoints per campaign in a Query Table fixed the fan-out.
Result
Campaigns ranked by leads and pipeline they actually generated, not by clicks — the basis for moving budget toward what converts.

CRM & Sales

Sales targets lived in a spreadsheet. Actuals lived in the CRM.

Problem: management wanted each sales agent's objectives compared to orders and deals in real time, but targets were set in Excel and nobody could see progress until month-end.

sales-performance.dashboard
Pipeline by stage (k€)
Lead source — share %
Target vs achieved, last 6 months
Win rate by sales rep
Challenge
Moved target-setting into a Zoho Analytics Data Form, so managers enter objectives directly where they're reported. Month-to-date compares against the same month of the previous year, not the previous month, because the business is seasonal.
What the data revealed
The first version showed some agents with targets several times higher than agreed: each target row was multiplied by the number of orders it joined to. Aggregating orders per agent and period before the join (SUM DISTINCT pattern) brought targets back to reality.
Result
Live target-vs-actual per agent; managers stopped rebuilding the comparison in Excel at month-end.

Helpdesk & Support

The time-worked report said tickets took seconds. They didn't.

Problem: the support team needed total time worked per ticket and per agent from Zoho Desk, to see workload and where effort really went.

support-analytics.dashboard
Tickets by priority, last 8 weeks
SLA compliance — trend
Avg. time worked (h) by category
CSAT — monthly trend
Challenge
Time entries sit one level below tickets, so totals per ticket double-counted as soon as tickets were joined to anything else; time was pre-aggregated per ticket first.
What the data revealed
The standard seconds-to-hours conversion produced absurd results. Checking raw values against Desk showed that in this instance time worked was already stored as decimal hours. The lesson I now apply everywhere: validate the unit against the source before writing a single formula.
Result
Reliable time-worked figures per ticket, category and agent — workload became a weekly metric instead of an impression.

Regulatory Reporting

A regulator wanted 14 numbers in a fixed layout. The data model produced none of them in that shape.

Problem: a telecom operator had to file a periodic report on customer reimbursements to the national regulator — a fixed row-by-row template, Italian number formatting, specific ordering. It was assembled by hand every period.

Synthetic values · one UNION ALL block per metric · comma decimal separator · fixed row order
Challenge
Unpivoted 14+ aggregate metrics into the regulator's row layout with UNION ALL in a Zoho Analytics Query Table, working within its limits: no parameters, a three-level cascade cap, and decimals forced to a period by to_string() — replaced with commas via REPLACE().
What the data revealed
Totals came out higher than the operator's own records. Each reimbursement request linked to several traffic records, and the join multiplied the amounts. A dedicated Query Table aggregating traffic per request before the join made the figures reconcile.
Result
The filing became a live report, ready in the required format every period instead of being rebuilt by hand.

CRM Data Migration

Before moving to a new CRM, nobody knew what was really in the old one.

Problem: clients arrived with exports from legacy CRMs, project tools and custom Excel trackers, expecting them to "just be imported" into Zoho CRM. Fields were decided on gut feeling, and bad data travelled into the new system.

Challenge
Built a standard field-mapping deliverable: each source field profiled with proposed Zoho CRM type, fill rate, distinct values and repetitions — pick list when ≤60 distinct values — plus a log of every cleaning intervention with original and cleaned values. Nothing overwritten silently, nothing invented to fill gaps.
What the data revealed
A meaningful share of "required" fields turned out to be always empty, dates hid fake placeholders, and the same company appeared under several spellings. The mapping turned "import everything" into a conversation about which data is worth migrating.
Result
The mapping became a named internal process with reusable templates, adopted across the team for every new client onboarding — including CRM-to-CRM migrations with duplicate checks on VAT number and company name.

HR & People Ops

The standard connector showed days off, not hours.

Problem: hourly permission fields (from/to) weren't surfaced by the standard Zoho People → Analytics connector, so remaining hour balances per employee couldn't be calculated. On top of that, the working-hours report had to follow strict business rules on rounding and weekly caps.

hr-analytics.dashboard
Headcount by department
Leave balance distribution
Turnover rate — quarterly trend
Time-tracking compliance by team
Challenge
Retrieved the missing from/to hour fields via the Zoho People API; implemented cascading rounding and weekly-cap logic in the hours report.
What the data revealed
Weekly totals were shifted by a day: the weekday function numbered Monday as 0, not 1. Since then I validate every date function against a known reference date before trusting it.
Result
Row-level security on the logged-in user's email (${System.login.email}): each employee sees only their own timesheet, HR sees everything.

AI & Automation

Two AI assistants built in-house to remove the most repetitive parts of the job.

Context: almost every case above started with the same two bottlenecks — messy source data before an import, and Zoho Analytics know-how that had to be re-solved every time someone hit the same wall. So I built tools for both.

01

ExcelliArmus

Data cleaning assistant · Zoho & Freshworks imports

Client files arrived in every format imaginable — inconsistent dates, duplicates, broken formulas, columns that matched nothing in the target CRM. Cleaning them by hand ate hours out of every import.

−60%
time the team spends on data quality before each import
  • Column mapping to Zoho and Freshworks import fields
  • Validation of formats, dates and required values
  • Joins across multiple source files, with fuzzy matching for near-duplicates
  • Delivered as a no-install Gemini Gem, plus two Python Flask versions: rule-based, and one running a local LLM (Ollama / Mistral) so client data never leaves the machine
Turned a multi-hour manual cleanup into a self-serve step the whole team runs before any import — with a privacy-first option for sensitive datasets.
02

Zoho Analytics Query Assistant

Query Tables · Formula troubleshooting

The lessons in this portfolio — fan-out on one-to-many joins, quoting rules that differ between Query Tables and formula columns, Query Table nesting limits, row-level security — used to live in one person's head.

  • Drafts aggregate formulas and Query Table SQL on request
  • Diagnoses fan-out and duplication in joined tables
  • Knows Zoho Analytics limits and suggests native features before custom SQL
  • Drafts clear technical support replies for clients in English
Standardized how the team writes and debugs reports — less tribal knowledge, faster onboarding on new projects.
